# Security and demo boundary

This application is designed for local portfolio demonstration with synthetic records. It refuses to start outside Development/Testing and is not hardened for internet exposure.

- Credentials and signing/service keys are randomly generated by scripts/setup.mjs into ignored .env.
- .env.example contains placeholders only. No production credentials or employer information are needed.
- JWT tokens validate signature, issuer, audience and lifetime. Operator mutations require a server-side role policy.
- Login and mutation endpoints are rate limited.
- Browser tokens remain in memory; only the theme preference is stored in localStorage.
- Mock business APIs require a service key. The dashboard does not receive that key.
- Input sizes, environments, scenarios, amount ranges and foreign customer references are validated.
- Logs use controlled messages and correlation IDs, not headers or raw bodies. Audit entries attribute actions to the fixed demo account name and role only.
- Sign-out, a 401 response or token expiry aborts in-flight dashboard requests and clears all protected data from memory. Late responses are discarded.
- Docker exposes only loopback ports and runs applications as non-root users.
- OpenAPI and health are intentionally anonymous on the local development network.

HTTP, shared demo passwords, a simple service key, schema auto-creation, no centralized identity, no distributed leases and no retention policy are intentional MVP constraints. Before a real deployment, replace demo auth with a maintained identity provider, add TLS and secret management, use migrations, define data retention and isolation, and perform a dedicated threat model and security review.

Never paste local credentials or tokens into public issues, screenshots or test artifacts. If a real secret is accidentally committed, revoke it immediately; deleting the current file does not remove it from Git history.
